## 0. 执行协议（必读，不可跳过）

1. **分批交付**：按批次顺序执行。完成一个批次 → 输出该批次的手动验收步骤 → **停下等用户确认通过** → 再开始下一批次。禁止一次做多个批次。
2. **前端测试**：实施 agent 不自己跑前端验证，完成改动后给用户具体手动测试步骤（访问哪个页面、点什么、应看到什么）。**后端改动**（接口/数据变化会影响前端的）实施 agent 需自测（curl 或临时脚本）后再交付。
3. **架构约定**（详见项目 CLAUDE.md，此处摘关键）：
   - 后端 Python 3.9：用 `Optional[X]`/`List[X]`（typing），禁 `X | None`；绝对导入（`from services.xxx import ...`）。
   - 新增路由响应统一用 `{"success": True, "data": ...}` 包装（前端 `unwrapData` 兼容两种格式）。
   - AI 客户端统一 `load_ai_client_from_config()`；结构化 AI 任务传 `temperature=0`，创意任务（改款推荐、设计搭配）**不传**。
   - 给 VLM/AI 的 prompt 里 **JSON 输出示例的可变字段必须用方括号占位符**（如 `"[这里填什么、怎么判断]"`），禁止写成看起来像正确答案的具体值（曾导致 VLM 模式匹配抄示例的事故）。
   - 前端动 `layout.tsx`/路由等 Next.js 结构前，先读 `frontend/node_modules/next/dist/docs/`（Next 16 有 breaking changes）。
   - JSON 落盘用 `services/file_utils.py` 的 `atomic_write_json`（已有）。
   - 上传路径安全：文件名一律 `Path(filename).name` 清洗；URL 路径转磁盘路径要校验前缀白名单、拒绝 `..`。
4. **工作区现状**：仓库有上一轮修复的未提交改动（属正常基线）。开工前建议先让用户确认是否把当前基线 `git commit` 一次，再动工；每批次完成并验收通过后各提交一次。
5. 生图 AI 配置在 `backend/data/config.json` / `backend/data/gen_config.json`（已 gitignore），**任何情况下不得提交、不得打印完整 key**。

## 3. 批次二：主题切换（需求1）

**目标**：全站支持浅色/暗色，默认暗色（与现状像素级一致），选择持久化，刷新不闪错误主题。

## 4. 批次三：Spike 带图验证 + 比例前置（需求6）

### 4.1 Spike：生图 API 是否支持参考图（决定批次四方案裁剪）

**背景**：生图双模式配置在 `backend/data/gen_config.json`（`api_type: openai|aireiter`）。两条待验证：
- **AIReiter 原生**（`POST {base}/api/openapi/submit`，body `{out_task_id, model, params:{prompt,width,height,...}}`）：`params` 是否接受图片输入？候选字段名依次实测：`images`（base64 数组 / data URI 数组 / URL 数组）、`image_urls`、`image`、`reference_images`。优先查 AIReiter 官方文档（如可访问）。
- **OpenAI 兼容**：`POST {base}/v1/images/edits`（multipart：`image[]` + `prompt` + `model`）是否被上游代理透传支持；顺带试 `/v1/images/generations` JSON body 加 `image` 字段是否被接受（个别代理的非标扩展）。

**做法**：写一个临时脚本（如 `backend/spike_ref_image.py`，读 gen_config.json 取 key，用一张小测试图 + 指令式 prompt 如 `Replace the main subject with a basketball, keep everything else identical`）逐一实测；查询任务结果确认**出图真的参考了输入图**（不只是接口不报错）。脚本验证完删除，**结论写入 CLAUDE.md**（新增一节"生图参考图支持"）：每种模式 支持/不支持、字段名与格式、最大张数、大小限制、耗时/计费变化。

**产出即闸门**：两种模式至少一种支持 → 批次四全量做；都不支持 → 批次四缩水为"仅编辑指令文本"（无真实图片输入），并明确告知用户此路不通。

### 4.2 需求6：比例约束前置 + 消除双比例矛盾

**改法**：
1. `backend/routers/image_gen.py` 的 `submit_gen_task`：构建 prompt 前加比例句。新增模块内辅助函数 `_ratio_text(width, height)`：gcd 化简，化简后任一边 >50 时近似到常见比例集 `{1:1, 3:4, 4:3, 2:3, 3:2, 4:5, 5:4, 9:16, 16:9}`（取比值最接近者）；朝向 = portrait/landscape/square。前置句：
   `[Canvas: {rw}:{rh} {orientation} format] The entire design must be composed for and fill this {rw}:{rh} canvas edge to edge. ` + 原 prompt。
2. 落库的 `task.prompt_positive` 存**前置后的最终值**（任务页可追溯实际发送内容）。天然幂等：前端传来的 prompt 永不含此句。
3. **删除** `backend/services/prompt_generator.py` 里两处规则卡画布比例片段（按内容定位）：`positive_parts.append(f"aspect ratio {canvas_ratio}")` 和 `prompt_parts.append("aspect ratio {}".format(ratio))`——它们来自 layer_4 的画布比例，与用户实选尺寸可能矛盾，以实选为准。中文结构化提示词里的画布比例展示不动。

### 批次三验收

- Spike：给用户看两种模式的实测结论表 + 参考图生效的对比图（若支持）。
- 比例：提交 3066×4000 任务 → 生图任务页该任务 prompt 以 `[Canvas: 3:4 portrait format]...` 开头（后端自测 curl 确认落库值）；全文只有这一处比例表述；竖/横/方各生一张目检构图朝向。

### 5.2 后端：编辑指令提示词（`image_prompt_edit`）

`backend/services/prompt_generator.py` 新增 `_build_edit_prompt(...)`，三个版本的返回 dict 各加字段 `image_prompt_edit`（与 `image_prompt_positive` 并存，组装自现有数据，**无新增 AI 调用**）：

**模板骨架**（英文，分行）：
```
Using the attached image as the base design, recreate it as a {target_product} print design with ONLY these modifications:
1. Replace {original} with {changed_to}.
2. ...
Keep everything else — composition, style, layout and all other elements — identical to the reference image.
Requirements: all visible text in the image must be English only; each text appears exactly once; clean printable design.
```

**各版本的 modifications 来源**：
- **版本B**（`generate_version_b`）：`recommended_changes_detail`（已有 `[{dimension, original, changed_to}]`）逐条转 `Replace {original} with {changed_to}.`
- **版本C**（`generate_from_selections`）：`selections` 与 layer_3 原值对比，只取 `chosen != original` 的维度（复用 `_build_change_summary` 的判定逻辑），同上格式。**无任何变更时** modifications 段写 `1. No element changes; faithfully recreate the base design.`
- **版本A**（`generate_version_a`）：无元素替换，modifications 为风格迁移指令：`1. Restyle with: {ref_visual_style} style.` `2. Recolor with: {ref_color_palette} palette.`（有构图参考再加一条；均取自已提取的参考图英文特征）。
- `target_product` 各版本调用处都有，作参数传入。

**值语言策略**（已与用户确认）：值优先取英文（`*_en` 字段 / `extract_english_part`）；取不到且含中文时**原样放行中文值**（编辑模式例外——模型看得到图中元素，中文值仅作定位标识；图中不出现中文由 Requirements 尾句兜底）。此处**不要**用 `_append_english` 的 CJK 丢弃策略。

**可定制项**：不在服务端烤入 edit prompt；前端勾选后 fragment 拼在 edit 文本末尾（与完整模式同机制，fragment 本身是合法的新增类指令）。

### 5.3 前端：双模式提示词 UI

`PromptDisplay.tsx`：
1. `PromptResult` 接口加 `image_prompt_edit?: string`。
2. 新 props：`hasRuleImage?: boolean`（由 `PromptVersionA/B/C` 传 `Boolean(ruleCard?.source_images?.length)`）。
3. 新增 state：`editableEdit`（初始 `result.image_prompt_edit || ''`，随 result 同步的 effect 与 `editablePositive` 同模式）；`useReference: boolean`——初始值 `hasRuleImage && !!result.image_prompt_edit && supportsReference`（`supportsReference` 从 `GET /api/gen/config` 拉，可在 PromptDisplay 挂载时取一次并缓存）。
4. **开关 UI**：`MergedPromptBlock` 正上方加一行：`🖼️ 附带竞品原图（编辑模式）` checkbox + 竞品小缩略图（`ruleCard.source_images[0]` 经 `/uploads/` 拼 URL，加载失败隐藏）。不可用时置灰 + 原因文案（`当前生图接口不支持参考图` / `该规则卡无竞品原图`）。
5. **模式切换逻辑**：激活文本 = `useReference ? effectiveEdit : effectivePositive`（`effectiveEdit` = `editableEdit` + 勾选 fragment，拼接逻辑与 `effectivePositive` 同构，可抽小函数复用）。`MergedPromptBlock` 显示激活文本；完成编辑回写到**当前激活模式**的 base（edit 或 positive）并复位勾选。两套编辑互不覆盖。负向提示词两模式共用 `editableNegative`。
6. `ImageGenSection` 新 props：`attachRuleImage: boolean`（=`useReference`）、`referencePaths: string[]`（本批次恒 `[]`，批次五启用）；submit body 加 `attach_rule_image`、`reference_image_paths`。

### 批次四验收

1. （后端自测）curl 提交 `attach_rule_image=true` 的任务：任务记录 `used_reference=true`；AIReiter/OpenAI 按各自支持方式带图；不支持的模式正常纯文本降级 + warning 日志。
2. 用户手测：打开有竞品图的规则卡 → 生成版本B → 提示词块上方出现开关（默认开）+ 竞品缩略图 → 提示词显示**短的编辑指令**（只含变化量，含 `Using the attached image as the base design`）。
3. 关闭开关 → 提示词切回完整描述版；再开 → 编辑指令回来；两边各自编辑后切换不丢失。
4. 用"足球→篮球"式实测：找一张有明确可替换元素的竞品图 → 版本C 把该元素换成别的 → 开着开关生图 → 出图与竞品构图/风格一致、仅该元素被替换。
5. 旧规则卡（无 source_images 文件）：开关置灰、文案正确、纯文本生图正常。
6. 生图任务页能区分带图/不带图任务（используя `used_reference`，列表项加一个小标记）。

## 6. 批次五：生图流程参考图上传（需求5）

   - 响应：`{"success": True, "data": {"fragment": ..., "description_cn": ..., "ref_path": "/gen-refs/xxx"}}`。
3. **前端**（`ImageGenSection` 生成按钮上方折叠区「➕ 添加参考图」）：

   - `ref_path` 存入 `referencePaths` state → 提交时进 `reference_image_paths`（批次四管道已就绪）→ 该图与竞品图一起作为图片输入附带（支持多图时）。

## 7. 批次六：完整描述模式分段重构（需求4 兜底优化）

## 8. 批次七：批量设计搭配（需求8）

### 8.1 后端 `POST /api/prompts/variants`

`routers/prompts.py` 新路由，请求 `{rule_id, target_product}`：
1. `get_rule` 校验存在；`load_ai_client_from_config()`（无 AI 返回 400，提示需配置——本功能强依赖 AI）。
2. 新 prompt（`prompts/prompt_generation.py` 加 `get_variants_prompt(rule_card_json, target_product)`）：基于规则卡 layer_3 的 alternatives 组合出 N 种**差异明显**的设计搭配，N 由 AI 在 3~6 内自定；锁死第 0 层核心卖点不可变；输出 JSON：
   ```
   {"variants": [{"name": "[搭配名-中文，简短]", "summary_cn": "[一句话说明元素搭配-中文]",
                  "changes": {"[维度名，必须来自规则卡可替换维度]": "[选择的替代值]"}}]}
   ```
   （示例全部用占位符，遵守约定）。创意任务，**不传 temperature**。
3. 服务端校验：过滤 `changes` 中不存在于 `layer_3.replaceable_elements` 的维度；variants 截断至 6。
4. 每个 variant 调 `generate_from_selections(rule_card, changes, target_product)` 组装完整提示词。**性能关键**：给 `generate_from_selections` 加可选参数 `skip_slots: bool = False`，variants 场景传 True 跳过 `_get_customization_slots_with_ai_fallback`（否则 6 个变体 = 6 次额外 AI 调用；批量 UI 也没有勾选框，不需要 slots）。
5. 响应：`{"success": True, "data": {"variants": [{name, summary_cn, prompt_positive, prompt_negative, prompt_edit}]}}`（prompt_edit 即批次四的 `image_prompt_edit`）。

### 8.2 前端 `BatchVariantsSection`

1. 先做两个小抽取（避免重复代码）：
   - `PRODUCT_SIZE_PRESETS` + `API_MAX_SIZE` + `calcRatioText` 从 `PromptDisplay.tsx` 移到 `frontend/components/prompts/sizePresets.ts`，原处 import（行为不变）。
   - `ImageGenSection` 的大图预览遮罩抽成 `frontend/components/ui/ImagePreviewModal.tsx`，原处复用。
2. 新组件 `frontend/components/prompts/BatchVariantsSection.tsx`，在 `PromptTabs.tsx` 三栏 grid **下方整行**渲染（props：`ruleId`、`ruleCard`）。
3. 状态机：`idle → loadingVariants → listReady → generating → done`。
   - idle：目标产品下拉（复用 `ProductSelect` + `getProductOptionsFromRuleCard`）+ 尺寸下拉（复用 sizePresets）+ 按钮「🎲 AI 设计搭配方案」。
   - listReady：显示 `AI 共给出 N 种设计搭配`，每种一行（名称 + summary_cn），**不渲染任何提示词**；按钮「▶ 批量开始生成（共 N 张）」。
   - generating：**前端 for 循环串行**——逐个 `POST /api/gen/submit`（`count:1`、`version:'batch'`、prompt 用 `prompt_edit`（若批次四判定支持参考图且规则卡有图，`attach_rule_image:true`）否则用 `prompt_positive`、宽高按 `API_MAX_SIZE` 等比缩）→ 轮询 `/api/gen/task/{id}`（5s 间隔、单个上限 5 分钟，与现有一致）→ 完成/失败后**再提交下一个**（串行防过载）。进度文案 `正在生成第 X/N 个：{name}`。
   - 结果区：按钮旁**横向滚动行**（`flex overflow-x-auto`），每张卡片 = 图 + 搭配名 + 状态（✅/❌/⏳）；单个失败标 ❌ 继续后续；全部结束显示 `完成 X/N`。点击图片 → `ImagePreviewModal`。
4. 已知限制（组件内小字注明）：批量进行中离开页面会中断，已完成的图可在生图任务页查看（version=batch）。

### 批次七验收

1. 点「🎲」→ 3~6 种搭配，各组合肉眼可见不同、核心卖点相关元素未被改动；全程无提示词展示。
2. 点批量生成 → 图片逐张出现在横向行、顺序与列表一致、进度文案正确；中途人为制造一个失败（如断网几秒）→ 该项 ❌、后续继续。
3. 点图开大图预览；生图任务页按 version=batch 能看到这批任务（含 used_reference 标记）。
4. （后端自测）variants 响应中 changes 维度全部合法、variants ≤ 6、无额外 slots AI 调用（看日志/耗时）。
